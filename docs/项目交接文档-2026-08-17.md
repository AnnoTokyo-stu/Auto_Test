## 1. 交接摘要

本项目是面向“中国电信银河数据跨境平台”的 Python Web UI 主流程自动化项目，采用 Selenium + Page Object + Pytest + Allure。默认浏览器为 Chrome，当前环境为生产环境，登录、注册和跨角色流程包含人工图形验证码，因此主要采用“自动填写与操作 + 人工验证码”的半自动方式。

`WEB-082`、`WEB-083` 和 `WEB-084` 已由用户于 2026-08-17 确认测试通过。当前数据产品标准订单正向状态链已经闭环：

1. 数据使用方对现有已上架产品下单；
2. 数据提供方审核通过；
3. 运营方（管理员）审核通过；
4. 数据使用方确认同一订单并上传模拟 Word 合同；
5. 验证订单进入“待确认合同”、合同进入“待确认”；
6. 数据提供方按同一订单确认合同通过；
7. 验证订单进入“待支付”、合同进入“已确认”；
8. 数据使用方按同一订单上传模拟 PDF 支付凭证并提交；
9. 验证支付后订单“待确认收款”、支付“已支付”；
10. 数据提供方确认款项到账并一次性交付“12g文件”；
11. 数据使用方验收通过；
12. 验证订单“已完成”、合同“已确认”、支付“已到账”、交付“已完成”、验收“验收通过”；
13. 打开同一订单详情，核对订单编号、产品编号和最终状态。

WEB-084 完整复用已通过的 WEB-083，再执行提供方确认收款、提供方交付、使用方验收和详情核对。确认收款结果值为 `E`；2026-08-17 实测确认到账后订单状态与交付状态均为“待交付”、支付状态为“已到账”。交付方式为“一次性交付”，现有数据资源名称为“12g文件”，验收结果为“验收通过”。

后续不要重新设计已经通过的 WEB-082～085、WEB-087、WEB-089 和 WEB-090。WEB-085 运营方审核不通过已由用户于 2026-08-17 确认真实执行通过，WEB-087 合同驳回重传及再次确认、WEB-089 未到账回退待支付、WEB-090 交付必填校验与取消已由用户于 2026-08-18 确认真实执行通过；WEB-086、WEB-088 的自动化实现已移除，但文件缺失、格式和大小校验仍作为手工/可控环境测试点保留在 Excel；WEB-091 已完成自动化首轮实现，WEB-092～095 已作为人工或受控环境用例写入主表。下一步真实执行 WEB-091 并校准批次交付、验收驳回和重新交付相关动态定位。Context7 只能提供第三方库文档，不能代替本交接文档保存项目业务上下文。

## 2. 用户明确提出的要求

### 2.1 初始项目要求

1. 在项目下的“自动化测试”文件夹中建设 Python 自动化测试项目。
2. 先找到既有测试用例，严格按照用例设计；测试用例版本较旧时，应根据实际测试过程修订主表，而不是强行遵循错误预期。
3. 参考用户的自动化测试笔记所述规范与知识点完善项目。
4. 使用 PO + Pytest 架构，遵循高内聚、低耦合：页面原子操作、页面对象、测试脚本、测试数据、配置、工具分离。
5. 目标结构为：

   ```text
   项目根目录/
   ├─ base/          # 通用页面操作
   ├─ page/          # 页面对象和业务操作
   ├─ script/        # pytest 测试脚本
   ├─ data/          # JSON 参数化数据
   ├─ log/           # 执行日志
   ├─ report/        # Allure 原始结果
   ├─ config.py      # URL、路径、等待等配置
   ├─ tools.py       # 驱动、日志、数据读取等公共工具
   ├─ conftest.py    # fixture 和执行保护
   └─ pytest.ini     # pytest 配置
   ```

6. 与用户协同开发，原则上按“设计 → 架构 → 具体代码 → 验收”推进；用户明确说“开始执行”或“直接修改”时直接实施。
7. 尽量符合企业级自动化测试标准。
8. 初期页面因网络问题无法访问时，允许保留 `TODO` 定位器，但必须提供定位填写指导。
9. 用户自行在 PyCharm 配置 C 盘 Python 解释器，项目只负责代码、依赖和运行命令。
10. 重点测试主流程，不要求穷举所有分支，可以按实际业务调整内容。

### 2.2 后续确认和新增要求

1. 页面入口访问后先跳转登录页。
2. 浏览器默认 Chrome，但浏览器、驱动、地址、等待时间均须参数化，避免大量修改代码。
3. 生产环境图形验证码和邮箱验证码不能固定，采用人工输入的半自动方式，不做验证码识别或绕过。
4. 账号密码保存在被忽略的 `.env.local`，禁止写入 JSON、代码、报告或交接文档。
5. 后续不能忘记继续补全剩余测试用例。
6. 页面内容较长时必须自动滚动；长表单填写应提高速度。
7. 对重复“详情”“审核”等按钮，优先自动识别目标行，不让用户手工指定固定行。
8. 实际流程与旧用例不一致时，今后都要同步修改 `测试用例.xlsx`。
9. “数据加工平台”不属于本项目组范围，不测试。
10. 数据产品、订单、合同等使用模拟数据，禁止上传真实客户资料、证件、合同或付款信息。
11. 订单审核、合同、支付、收款确认、交付和验收通过主流程已实现；下一阶段覆盖验收驳回与重新交付异常分支。
12. 产品订单流程从现有已上架产品下单开始，不必每次从创建产品开始。
13. 减少重复检测和不必要等待，提高执行与代码生成速度，但不能牺牲目标唯一性和生产安全。

## 3. 不可破坏的设计规范

### 3.1 分层与职责

- `base/base_page.py`：只提供通用原子操作，不包含具体页面业务断言。
- `page/*.py`：元素定位器与页面业务动作放在 Page Object 中。
- `script/test_*.py`：只负责编排业务步骤、Allure step 和最终断言。
- `data/*.json`：业务输入与预期状态参数化；账号密码不得进入 JSON。
- `config.py`：环境可变项全部从环境变量读取。
- `tools.py`：驱动、日志、JSON、唯一名称、敏感信息遮蔽等公共能力。
- `conftest.py`：浏览器、账号 fixture、跨角色重新登录、执行保护和失败取证。

页面对象之间应复用基础能力，但不要把某个页面的业务操作塞进 `BasePage`。测试脚本不直接堆砌长 XPath。

### 3.2 定位器规范

1. 优先使用稳定属性、业务文本和局部容器作用域。
2. 弹窗定位必须限定“当前可见弹窗”，避免命中页面中隐藏的历史弹窗：

   ```xpath
   //body/div[contains(@class,'el-dialog__wrapper')]
   [not(contains(@style,'display: none'))]
   ```

3. 列表操作禁止只使用 `nth-child`、固定行号或第一个按钮。
4. 同名按钮必须先唯一匹配业务行，再在同行操作列内找按钮。
5. 横向滚动 Element UI 表格中，`WebElement.text` 可能丢失隐藏列内容；读取完整行时使用 DOM `textContent` 并压缩空白。
6. 主表与右侧固定操作列应按可见行索引映射，且必须校验两侧行数一致。
7. 定位器未补全时使用 `todo_locator("描述")`，框架会抛出 `LocatorNotConfiguredError`，不得静默点错元素。
8. 元素定位原始资料保存在 `元素定位/`，修改定位前优先查阅对应文件。

### 3.3 等待与输入规范

1. 使用显式等待，不使用固定 `sleep` 作为主要同步手段。
2. 点击、输入前通过 `scrollIntoView` 将元素滚动到视口中部，兼容长页面和可滚动容器。
3. 长表单默认启用 `WEB_FAST_INPUT=true`：使用原生 value setter，并触发 `input`、`change` 事件。
4. 个别控件不兼容快速输入时，在 `.env.local` 设置 `WEB_FAST_INPUT=false` 回退 `send_keys`。
5. 密码强度、逐键联动等专项用例必须使用真实键盘输入，不应使用快速赋值绕过前端行为。
6. 文件 `send_keys` 只表示浏览器选中了本地文件，不等于前端异步上传完成；提交表单前必须等待上传成功状态。
7. 日期时间弹层挂在 `body` 下，不能只在订单弹窗内部查找；应按当前可见 popper 的专用类定位。

### 3.4 动态数据与唯一匹配

1. 新建产品使用 `unique_name()` 追加时间戳和随机后缀，避免名称冲突。
2. 管理员审核产品时使用运行时完整名称筛选，并要求结果唯一。
3. 产品市场搜索可能不真正过滤卡片，因此先尝试编号搜索，再从可见卡片按名称前缀唯一匹配，进入详情后复核产品编号。
4. 新订单使用产品编号、初始状态和订单编号中的 `YYYYMMDDHHMMSS` 时间识别。
5. 跨角色流程必须传递并复用同一个动态订单编号，不能在不同角色页面重新“取第一条”。
6. 找不到唯一目标时立即失败，禁止退化为随机点击。

### 3.5 生产环境安全规范

1. 默认 `pytest` 只收集并跳过真实 UI。
2. UI 用例必须显式传 `--run-ui`。
3. 会写数据的用例必须显式传 `--run-destructive`。
4. 高风险操作还需要独立的生产确认参数：

   - 注册：`--confirm-production-registration`
   - 提交数据产品审核：`--confirm-production-product-submission`
   - 管理员审核数据产品：`--confirm-production-product-approval`
   - 产品上下架和变更：`--confirm-production-product-lifecycle`
   - 创建采购订单：`--confirm-production-product-order`
   - 提供方审核订单：`--confirm-production-order-provider-audit`
   - 运营方审核订单：`--confirm-production-order-operations-audit`
   - 上传订单合同：`--confirm-production-order-contract-upload`

5. 每一步只操作通过名称、编号和状态唯一确认的目标对象。
6. 上传材料必须来自 `test_materials/`，不得使用真实证件或合同。
7. 日志不得输出密码；账号、手机号等需要输出时应遮蔽。

### 3.6 用例与文档规范

1. pytest 测试函数保留 Excel 的 `WEB-xxx` 编号。
2. `测试用例.xlsx` 是业务用例主表；实际流程变化后同步修订并增加版本记录。
3. “已构建”不等于“真实环境通过”，交接和报告中必须区分。
4. 失败时依次检查：终端 traceback、`log/web.log`、`screenshots/`、Allure 附件。
5. 新增复杂流程后更新对应运行指南。
6. 剩余用例仍需逐批补齐，不能因为主流程能跑就宣称全部完成。
