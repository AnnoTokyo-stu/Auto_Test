# 数据产品管理自动化运行指南

## 覆盖范围

- `WEB-075`：同一次登录中创建 3 个不同业务场景的数据产品草稿。
- `WEB-076`：创建 1 个资料完整的数据产品并提交审核。
- `WEB-077`：提供方提交产品，清理会话后切换超级管理员审核通过，再切回提供方复核结果。
- `WEB-078`：提供方产品审核通过后完成上架、下架，修改已下架产品并提交变更审核，再由管理员二次审核通过，最后切回提供方复核结果。
- `WEB-079`：提供方创建并上架唯一产品，独立数据使用方在交易市场精确搜索并提交采购订单；不覆盖订单后续审核、合同、支付和交付。
- `WEB-080`：数据使用方对现有已上架产品下单，提取动态订单编号，数据提供方审核通过并验证订单状态。
- `WEB-081`：数据使用方对同一现有产品重新下单，数据提供方审核不通过并验证拒绝状态。
- `WEB-082`：数据使用方下单、提供方审核通过、运营方审核通过，切回使用方确认同一订单后上传模拟 Word 合同。
- `WEB-083`：完整复用 WEB-082 前置流程，提供方确认合同通过后，数据使用方为同一动态订单上传模拟 PDF 支付凭证并提交支付。
- `WEB-084`：完整复用 WEB-083 前置流程，提供方确认款项到账并一次性交付现有数据资源，数据使用方验收通过后打开详情核对完整状态。
- 数据加工平台不属于本项目测试范围，不作为产品新增的前置自动化步骤。

模拟数据统一配置在 `data/data_product.json`，测试附件位于 `test_materials/`。产品名称在运行时自动追加时间戳和随机后缀，避免重复名称冲突。

当前产品提交必填“合规策略模板”，模拟数据统一选择“测试模版”。提交操作会同时监听弹窗关闭、成功提示、错误提示和表单校验；若页面拦截提交，失败信息会直接指出缺失字段，不再只返回无上下文的超时。

产品封面和产品图片属于异步上传。页面使用的自定义组件不一定生成标准 Element UI 成功节点，因此框架兼容上传列表、预览图和上传按钮隐藏等信号；若页面未暴露完成状态则继续填写，并在提交明确返回“请上传产品封面图”时自动重新上传一次后重提，避免无意义等待 30 秒。

## 提交审核

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_076_submit_product_for_review --run-ui --run-destructive --confirm-production-product-submission -s
```

生产环境提交审核受三层保护：用例必须同时提供 `--run-ui`、`--run-destructive` 和 `--confirm-production-product-submission`。普通回归不会误提交审核。

## 跨角色审核通过闭环

管理员账号保存在本机 `.env.local` 的 `TEST_ADMIN_NAME`、`TEST_ADMIN_PASSWORD` 中，项目代码与报告不会打印密码。执行过程中需要依次为数据提供方、管理员、数据提供方人工输入三次图形验证码。

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_077_provider_submit_and_admin_approve_product --run-ui --run-destructive --confirm-production-product-submission --confirm-production-product-approval -s
```

用例使用运行时唯一产品名称，在管理员列表筛选后要求只匹配一条记录；匹配数量不为 1 时会停止，不会审核其他产品。

管理员审核仍保留产品名称查询：它能把结果缩小为一条并避免目标产品位于后续分页。查询后会再次按产品名称列做完全匹配；固定操作列的“审核”按钮若被横向滚动表格遮挡，则仅对已经唯一确认的同行按钮使用 DOM 点击，不会按行号或随意选择第一条记录。

角色切换兼容两种登录落点：数据提供方登录后先进入门户首页，再打开运营管理后台；超级管理员登录后通常直接进入运营后台，框架会识别现有侧边栏并跳过重复入口点击。登录成功按本次账号显示名校验，不再依赖普通用户首页专用的 CSS 结构。

## 上架、下架、变更及二次审核闭环

该用例自行创建唯一产品并完成首次审核，然后严格按“唯一产品名称 → 唯一表格行 → 同行操作按钮”执行上架、下架和变更，不使用固定行号，也不会操作名称相似的其他生产产品。变更内容为产品简介；提交变更后再次切换超级管理员，在数据产品审核页完成二次审核通过，最后切回提供方验证“已下架/变更审核通过”。

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_078_product_on_off_shelf_and_submit_change_review --run-ui --run-destructive --confirm-production-product-submission --confirm-production-product-approval --confirm-production-product-lifecycle -s
```

执行时需要依次输入数据提供方、管理员、数据提供方、管理员、数据提供方共五次图形验证码。三个生产确认参数缺少任意一个时，用例都会跳过。

## 浏览器启动优化

本机 `.env.local` 已配置 `WEB_DRIVER_PATH`，直接复用与 Chrome 主版本一致的本地 ChromeDriver，避免 Selenium Manager 每次在受限网络中在线解析驱动。页面加载策略设为 `eager`，浏览器等待 `DOMContentLoaded` 后即交由显式等待接管，不再等待图片等全部静态资源加载。

## 现有产品下单与提供方审核

`WEB-080` 和 `WEB-081` 不再创建、审核或上架数据产品，直接使用产品编号 `DP20260814095528004`。每条用例登录后先进入数据交易市场下单。由于当前市场按产品编号搜索后仍可能展示全部商品，脚本会从所有可见卡片中按产品名称前缀唯一匹配，并进入详情复核产品编号后才允许下单。下单成功后点击“立即前往”，只确认已进入数据使用方订单管理，不在此处阻塞跨角色流程；随后立即清理会话并登录数据提供方。由于提供方侧边栏菜单在实际执行中多次出现“页面可见但 Selenium 定位不到”的现象，脚本不再依赖该菜单交互，而是在提供方登录会话建立后直接打开稳定路由 `/dataAssetTrade/product-order` 并校验 URL。该方式不会绕过登录或角色权限，只替代不稳定的导航点击。进入列表后通过产品编号、初始状态以及订单编号中的 `YYYYMMDDHHMMSS` 时间识别本次最新订单。订单行统一读取完整 DOM `textContent`，不受横向表格裁剪或隐藏列影响，也不依赖创建时间列。识别成功后按订单编号映射主表与固定操作列，不依赖固定行号或查询条件。

## 运营方审核与合同上传

`WEB-082` 沿用 WEB-080 的动态订单识别和固定操作列行映射，不依赖固定行号。运营方登录后从“数据产品交易 → 产品订单审核”进入审核列表，按同一订单编号审核通过；状态应从“待运营方审核”进入“待上传合同”。随后切回数据使用方，先复核订单编号、产品编号和状态，确认无误后才点击该行“上传合同”。

上传材料为 `test_materials/mock_data_product_purchase_contract.docx`，文件正文明确标注仅用于自动化测试。上传成功后预期订单状态为“待确认合同”、合同状态为“待确认”，支付、交付和验收状态保持不变。

脚本先填写备注，再选择模拟合同，并等待上传完成（最长 30 秒）后才点击“提交合同”。优先识别标准 `is-success`；当前合同组件未暴露该类时，改由“目标文件卡片已显示、单文件上传入口已隐藏、没有失败或上传中节点”联合判断，并要求状态连续稳定后才提交。合同弹窗使用标题和“提交合同”按钮作为稳定作用域，不依赖上传后会被组件移除的 `input[type=file]`；等待轮询也使用无阻塞元素查询。若上传失败或选中了意外文件，脚本会停止提交，避免文件卡片已经显示但表单仍提示“请上传合同文件”的竞态问题。若弹窗已因提交完成而关闭，脚本不会重复点击，而是直接刷新并核对同一订单的最终状态。

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_082_operations_approve_and_consumer_upload_contract --run-ui --run-destructive --confirm-production-product-order --confirm-production-order-provider-audit --confirm-production-order-operations-audit --confirm-production-order-contract-upload -s
```

执行时需要依次为数据使用方、数据提供方、管理员、数据使用方输入验证码；首次数据使用方下单后切换提供方，最后再次回到使用方上传合同，共四次登录、三个角色。四个生产确认参数缺少任意一个时，用例都会跳过。

## 提供方确认合同与使用方支付

`WEB-083` 每次从现有已上架产品下单开始，完整执行提供方审核、运营方审核和使用方上传合同，再继续合同确认与支付。所有角色都使用同一个运行时动态订单编号，任何阶段不能按固定行号或历史订单操作。

提供方点击同行“确认合同”，选择 `PASS`（合同通过）、填写确认意见并提交。根据当前页面截图，确认后预期状态为：订单“待支付”、合同“已确认”、支付“待支付”、交付“未交付”、验收“未验收”。随后切回数据使用方，点击同行“去支付”，上传 `test_materials/mock_payment_voucher.pdf`，等待文件卡片稳定后点击“提交”。该 PDF 醒目标注为自动化测试专用，不包含真实银行账户、签章、客户身份或交易数据。

WEB-083 已由用户真实执行通过，支付提交后的实际状态确认是订单“待确认收款”、支付“已支付”。

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_083_provider_confirm_contract_and_consumer_pay --run-ui --run-destructive --confirm-production-product-order --confirm-production-order-provider-audit --confirm-production-order-operations-audit --confirm-production-order-contract-upload --confirm-production-order-contract-confirmation --confirm-production-order-payment -s
```

## 确认收款、交付、验收与详情核对

`WEB-084` 从现有产品重新创建一笔动态订单并完整复用 WEB-083。支付成功后切换数据提供方，按同一订单点击“确认收款”，选择 `E`（确认到账）并填写模拟收款备注；实测订单状态与交付状态均进入“待交付”，支付状态进入“已到账”。随后在同一提供方会话点击“去交付”，选择“一次性交付”和现有数据资源“12g文件”，提交后预期订单“待验收”、交付“已完成”、验收“待验收”。

最后切回数据使用方，按同一订单点击“确认验收”，选择“验收通过”并填写意见。完成后严格核对订单“已完成”、合同“已确认”、支付“已到账”、交付“已完成”、验收“验收通过”，再打开同行“查看详情”，验证动态订单编号、产品名称、产品编号及上述最终状态均存在。详情读取仅限点击后出现的可见弹窗、抽屉或发生 URL 变化的详情页，不会把列表背景文本误当成详情。

```powershell
python -m pytest script/test_04_data_product_management.py::test_web_084_provider_deliver_and_consumer_accept_order --run-ui --run-destructive --confirm-production-product-order --confirm-production-order-provider-audit --confirm-production-order-operations-audit --confirm-production-order-contract-upload --confirm-production-order-contract-confirmation --confirm-production-order-payment --confirm-production-order-receipt-confirmation --confirm-production-order-delivery --confirm-production-order-acceptance -s
```

执行时需要依次人工完成八次验证码：数据使用方 → 数据提供方 → 管理员 → 数据使用方 → 数据提供方 → 数据使用方 → 数据提供方 → 数据使用方。确认收款、交付、验收分别使用独立生产确认参数，缺少任意一个时用例都会跳过。

## 当前限制

当前定位资料只提供了“一口价”的参数字段，因此本轮通过不同场景、任务类型、难度、格式、数据类型、币种和交付周期覆盖多种产品。后续需要测试“按阶梯定价”和“按质量定级定价”时，应先补充两种模式切换后出现的参数字段定位。
